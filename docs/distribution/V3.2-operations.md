# V3.2 operations and pilot procedure

## Migrate before deployment

Take a database backup and validate the existing migration journal first. Apply core `0106` and `0107` through `pnpm db:migrate`, and Hub `0006` and `0007` through `pnpm --filter @satsang/distribution-db migrate` with its dedicated migration-role connection. Reapply `packages/distribution-db/ops/runtime-grants.sql` using the existing deployment procedure and `distribution_runtime_role` variable. Never run migrations on application boot or give the Hub runtime role core access.

Core creates nurturing preferences, goal/current/history, projection/checkpoint and reviewed-content-policy tables. It adds nullable `view_entries.accepted_timezone`. The INSERT trigger snapshots the profile timezone for new rows; legacy history remains NULL rather than guessing past timezone. Saved `entry_date` remains authoritative. The existing append-only trigger is strengthened to compare every column except the narrowly permitted `user_id → NULL` erasure transition.

Hub creates immutable native source/analysis/review history and a separate language-reviewer grant table. Runtime can insert history and read grants; it cannot delete/rewrite history or grant itself reviewer eligibility. `0007` adds a monotonic proposal sequence so transaction timestamp order cannot revive an older analysis. Existing V3.1 rows are not rewritten.

All twelve new flags are inserted OFF with conflict preservation. Use existing feature administration audience stages. Native parent + integrity + candidates + review gates must be enabled for new native derivative actions. Shadows/glossary additionally require their own flags. Disable a flag to block new interaction without deleting history.

## Private media storage

The Hub web and render worker share `@satsang/distribution-assets`. The default backend remains private local disk. Explicit `DISTRIBUTION_ASSET_BACKEND=s3` selects the AWS SDK adapter for uploaded master bytes and generated video, captions and manifest files. Post/blog text, approval history, source relationships and file descriptors remain in PostgreSQL. Download archives are assembled through the authorized export route; they are not retained as separate S3 objects. External YouTube references remain references unless an authorized source file is separately uploaded.

Configure every S3 setting in `.env.example`: `DISTRIBUTION_S3_BUCKET`, `DISTRIBUTION_S3_REGION`, `DISTRIBUTION_S3_EXPECTED_BUCKET_OWNER` (the twelve-digit account ID), and `DISTRIBUTION_S3_PREFIX`. Stage `TEST` requires `test/`; `LIMITED` and `ON` require `production/`. Use separate test and production buckets and IAM roles as well. The authenticated operator's world must also match that prefix: TEST operators use the TEST deployment for media, even though the general `ON` audience admits them. Invalid configuration or a world mismatch refuses storage access; it never falls back to disk. The dedicated settings do not reuse core `S3_BUCKET`. Use the SDK credential provider chain with workload IAM roles rather than embedded credentials.

Objects use generated immutable keys under the configured prefix. Writes request AES256 server-side encryption, SHA-256 verification and `If-None-Match: *`; reads verify bounded size, checksum and media type before returning bytes. The expected bucket owner is sent on every operation. Bucket and object URLs are never returned to the browser: existing authenticated Hub routes retain role, rights, world, freshness and approval checks, including permission refresh after storage reads. S3 storage does not publish content or change Ashrama branding rules. These request controls follow the official [PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), [GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html) and [DeleteObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html) contracts.

With S3 selected, the worker also requires `DISTRIBUTION_RENDER_SCRATCH_ROOT`, an absolute private directory outside the repository and public/static paths. Each job verifies and stages its source in a private temporary directory, renders with the existing bounded FFmpeg adapter, uploads verified outputs, and removes scratch files. A lost database commit acknowledgement preserves durable output. Upload metadata cleanup occurs only after a proven rollback; uncertain writes are retained for later reconciliation. Do not run blanket prefix cleanup or lifecycle expiry against referenced content.

This local implementation does not provision a bucket, change AWS IAM, migrate existing local assets, or activate a production worker. Before an authorized AWS rollout, provision a private general-purpose bucket with public access blocked, bucket-owner-enforced ownership, TLS-only access, encryption, versioning and scoped object permissions (`GetObject`, `PutObject`, `DeleteObject` only within the selected world prefix). Keep broad listing, ACL mutation and bucket management outside the runtime role. Independently verify those deployed settings and exercise upload, rendering, role revocation and approved export in the AWS test environment. The worker's existing TEST-stage and loopback-database restrictions still apply; production worker authority/network adoption remains a separate release gate.

Switching a backend does not migrate old files. Before switching an environment with existing content, copy its explicitly inventoried referenced keys, verify every stored descriptor against destination bytes, then switch web and worker together during a controlled pause. Keep the original storage for rollback and reconcile any writes made after the switch before reverting. No such migration has been run by this change.

Local qualification on 5 October 2026: the full guardrail/lint/core-and-mobile type/test gate passed with 3,355 tests passing and 297 environment-gated tests skipped. The Hub production build and documentation check passed. All six Chromium/WebKit source workflow and current-role browser cases passed. The focused 49-test storage/render/database run includes actual FFmpeg encoding, verified output readback, stale-result cleanup, uncertain upload/commit preservation and timeout handling. S3 contract tests exercise the real SDK's signed request serialization through an in-memory handler; they do not claim live AWS bucket/IAM acceptance. Existing local preview settings and media were retained.

## Media naming and master lineage

New rendered files are grouped by immutable IDs under `distribution/derived/<master-id>/<source-version-id>/<derivation-id>/`. Local disk and S3 use the same relative keys. The filename family is `SGS_m<master-id>_<destination>_<format>_<language>_<aspect>_d<derivation-reference>` with `.mp4`, `_captions.vtt` and `_manifest.json` endings. For example, an Instagram video uses `SGS_m11111111-1111-4111-8111-111111111111_instagram_video_te_9x16_d333333333333.mp4`. The directory and manifest retain the full source-version and derivation UUIDs; the filename uses the first twelve hexadecimal characters of the derivation UUID. The manifest also records the exact raw storage key and source checksum.

The destination is selected in Variant Studio and bound into the immutable recipe. It labels intended placement; it does not assert that an Admin approved or published the file. Unassigned historical/manual assets say `manual-export`. Social activation exports use their reviewed destination, including YouTube, Facebook, Instagram, X and Reddit. Downloaded source archives share the `SGS_m<master-id>` reference and include their source version number. Archive member names and download names use the same safe naming rules without title text, private prose, path traversal or filename truncation.

Existing storage keys and approved recipe hashes remain readable. They are not rewritten on deployment; downloads of legacy derivatives receive the new names using their canonical master/job context. Source replacement produces a new source-version directory. Re-rendering produces a new derivation directory. Approval state stays in the database and manifest rather than mutating filenames. The standalone TEST content-pack generator likewise gives each platform its own filenames carrying the source reference and checksum, and records each file's source clip/time/segment lineage in its manifest.

Phone widths 320/390 and desktop width 1440 had no horizontal overflow. [The local naming receipt](evidence/asset-naming-local.json) records channel/master associations and hashes. The earlier sample package remains intact; the new package remains TEST/review-required and was not published.

## Projection backfill and recovery

Core requests a projection on the owner's normal home/API visit; goal changes also request reconciliation. The existing worker schedules the dedicated pg-boss queue every two seconds with a minute schedule as a recovery fallback. Each transaction reads at most 500 canonical rows and persists a cursor. Complete calendar days reconcile compensating rows together; published views are replaced only after the checkpoint finishes. Goal changes restart a stale checkpoint safely.

For a controlled cohort backfill, use the explicit operator tool:

```sh
pnpm exec tsx ops/rebuild-nurturing.ts TEST
pnpm exec tsx ops/rebuild-nurturing.ts TEST <nextCursor> 100
```

Use `PROD` only during an authorized rollout with the correct core connection. Each call scans at most 100 active users, honors feature audiences, excludes Sri Swamiji, and queues work without touching canonical credits. Repeat with the returned cursor until `more:false`. The worker remains responsible for reconciliation. A failed projection cannot roll back an accepted offering; the client shows “Progress is updating.”

For recovery after a bug, deploy the corrected projector, request affected users again and allow the normal worker to complete their checkpoints. If the algorithm/checkpoint format changed, an operator may clear ONLY the derived `nurturing_projection.checkpoint` in the affected world before requesting rebuild. Never edit/delete ledger rows, reset goal history or recalculate past local dates from today's timezone.

## Native evaluation

No live provider is configured by default. Supply documented contract and retention approval identifiers, an explicitly selected model and a secret key through the approved secret mechanism. The semantic runner reads only explicitly named local input files; each `NativeSemanticInput` contains an approved public transcript, source annotations, versioned glossary, authorization basis and shadow preference. Confidential content is excluded.

```sh
pnpm --filter @satsang/distribution-worker native:evaluate manifest.json private-output-directory 1
pnpm --filter @satsang/distribution-worker native:benchmark reviewed-corpus.json new-report.json
```

`manifest.json` is `{ "schemaVersion": 1, "jobs": [{ "id": "video-001", "inputPath": "/absolute/path/input.json" }] }`. Run one process per output directory. The per-invocation cap is 1–5 jobs; each source has three persisted attempts maximum. Completed outputs are validated and reused without another vendor call. Changed input under the same job ID is refused: create an explicitly new evaluation ID. A crash preserves the consumed attempt. The adapter bounds input, response size, output tokens and request time. Do not automatically retry a cost/quota incident indefinitely.

Required adapter environment names are `NATIVE_OPENAI_API_KEY`, `NATIVE_OPENAI_MODEL`, `NATIVE_PROVIDER_CONTRACT_APPROVAL`, and `NATIVE_PROVIDER_RETENTION_APPROVAL`. The tool does not grant approval from these strings: the deployment owner must record genuine adoption decisions. Keys, transcripts and provider error bodies are not written to health events.

Import normalized proposals in Native teaching review after the exact source transcript has been approved. Operator imports are marked as manual imported proposals rather than claiming a live model was called by the UI. The offline report retains the actual evaluation provider/model. Reviews require existing `content.review` capability plus an administrator-provisioned `native_reviewer` grant for the source language and matching TEST/PROD world. Use existing operator identity IDs; never link accounts by email.

A reviewer must record evidence for all ten checks and a decision reason. Boundary edits create a new proposal and require review again. Transcript corrections create a new authoritative transcript version. The native source governs; English shadows cannot become official translations automatically. The approved boundary opens Variant Studio; artifact approval is still required afterward. The longer teaching template permits complete teachings up to ten minutes, but the local renderer's CPU/wall/output budgets remain enforced: a resource-limit failure requires production render capacity planning, never truncation of meaning.

The corpus JSON has `schemaVersion`, `provider`, `model` and `samples: NativeBakeoffSample[]` (type in `packages/distribution-domain/src/native-bakeoff.ts`). Each sample records a distinct source checksum, authorized reviewer, native language, 3–5 reference moments, independently reviewed candidate outcomes, errors and baseline/review time. Use a separate report per provider/model/configuration. An empty example is included in this directory. Real corpus readiness does not automatically approve a release.

## Metrics and actionable alerts

| Signal | Delivered surface/event | Action |
| --- | --- | --- |
| Projection failures | `nurturing.projection.failure` and admin reconciliation totals | Alert on any failed batch; inspect worker/schema availability, then resume bounded rebuild |
| Projection lag | `nurturing.projection.batch.maximumLagMs`; warning `nurturing.projection.backlog` above 60 seconds | Alert if sustained across three batches; compare the five-second normal-condition target, worker capacity and long histories |
| Recommendation unavailable | `nurturing.recommendation.unavailable` | Alert on sustained failures; preserve catalogue/practice availability and inspect existing eligibility dependencies |
| Native processing | `distribution.native.processing` with duration, status, attempt and input hash | Alert on failed attempts, increasing latency, or exhausted three-attempt cap; inspect vendor quota/contract/cost controls |
| Native review backlog/uncertainty | Current analysis counts in Native teaching review | Investigate increased low-confidence spans with authorized reviewers; never auto-clear uncertainty |
| Corpus metrics | `distribution.native.benchmark` + saved full report | Block native rollout until real reviewer evidence and approved quality thresholds exist |

Feature administration shows weekly distinct participation, first practice within seven days, four-week retention and goals whose windows have ended. Activation cohorts are registrations 7–28 local days ago; retention cohorts are activated registrations 28–56 local days ago, measured on days 22–28 since registration. Rates are withheld when projection coverage is incomplete. Counts below ten and identifying complements are suppressed. Cancellations/extensions are shown separately. These are operational participation measures, never spiritual scores.

No outbound alert channel was configured. Route these structured events into the existing approved observability stack during the pilot; do not send private timeline bodies, source text, reflections or confidential records. Duplicate-credit and reconciliation anomalies continue to use existing canonical-ledger guardrails. No new nurturing reminders are dispatched, so complaint/unsubscribe/dismissal rates are not invented.

## Controlled pilot

1. Apply additive migrations in staging, keep flags OFF, verify existing signup/home/catalogue/live/SGS Posts and accounting parity.
2. Use TEST fixtures and designated operator/native reviewer grants. Verify source/rights/identity/role revocation, private-world isolation and refusal of unreviewed candidate exports.
3. Enable nurturing flags for the smallest controlled existing audience; review actual content metadata first. Verify goal progress latency, pause intervals, corrections and saved-date behavior. Collect explicit voluntary feedback; preferences do not enable communication consent.
4. Complete the real corpus bake-off and provider adoption. Enable native intelligence only for the authorized reviewer pilot. Maintain native review plus existing artifact review for every derivative.
5. Complete device, localization, accessibility and load acceptance; review baseline measurements and decide rollout. No claims of retention or production performance improvement before measurement.

## Rollback

Turn the new flags OFF in the existing registry, stop explicit evaluation invocations and pause the nurturing job if necessary. Revert application code to the prior compatible deployment while leaving additive tables/history intact. Existing canonical practice and shared pledges remain authoritative and usable. No schema/table drop is needed for operational rollback.

Do not drop `accepted_timezone` or weaken ledger immutability to roll back a screen. Historical goals, decisions and source governance must survive. If a schema removal is later explicitly required, take/export a verified backup and plan a dedicated migration after retention/erasure review. Queued bounded local renders may finish internally after flags are disabled, but approval/export require the fresh flag gate. No paid native jobs run implicitly.
