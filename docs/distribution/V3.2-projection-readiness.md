# V3.2 personal-goal projection readiness

Local TEST qualification, 3 October 2026. These measurements use generated `@example.test` identities and disposable PostgreSQL databases on the local Colima service at port 5442. No production, shared preview, reviewer, or team account was used. Each test database is dropped after the run; canonical rows are never edited or deleted.

## Changes

The previous worker advanced one 500-row page per two-second queue tick. A devotee with a modest historical ledger therefore needed several ticks before any goal progress was published. The worker now gives each selected devotee one page before offering another page to the same devotee. A turn stops scheduling new pages after 25 attempts or 1.5 seconds. Every page remains a separate transaction with a durable checkpoint. SQL statements have a transaction-local 1.5-second deadline and a 250 ms lock deadline; an in-flight statement can finish after the scheduling budget. The ordinary credit path does not invoke or await this worker.

The nurturing queue retains its two-second enqueue tick and explicitly uses a 0.5-second pg-boss polling interval. The web card's bounded “updating” polling now uses two seconds. PostgreSQL supplies projection request timestamps, cutoff timestamps, attempt timestamps, and lag telemetry. Published cutoffs retain PostgreSQL microsecond precision rather than passing through JavaScript millisecond truncation. This avoids false pending work and misleading lag caused by host/VM clock differences.

Blocked actor locks, ineligible flag audiences, and failed projections advance their attempt timestamp so that another pending devotee can proceed. Batch metrics now distinguish pages processed, projections completed, busy locks, failed actors, rows of pending work selected, and maximum request lag. Projections publish atomically after all pages reconcile; existing published data remains visible while a rebuild is incomplete.

## Measured evidence

Recorded focused run: **22 tests passed across four files** in 14.40 seconds. The database, domain, and real queue tests ran concurrently. This is local qualification, not a production capacity or network-latency guarantee.

| Scenario | Latest measurement | Verified behavior |
| --- | --- | --- |
| One devotee, 2,500 historic rows plus one new accepted offering | 1,037 ms processing; six pages | Completed goal, 100 newest facts, first practice from 2010, no remaining checkpoint |
| Real pg-boss path, same 2,501-row ledger | **2,424 ms acceptance to published projection** | Actual two-second tick and 0.5-second queue poll; completed goal readable from the database |
| 25 pending devotees, 101 ledger rows each | 1,156 ms batch processing | All 25 published in one fair batch in this focused run; no failures |
| 20,001-row ledger spanning 2,002 saved local dates | 25 pages in the first turn; 16 pages in the next, which took 426 ms | Durable continuation, all historical dates retained, goal progress preserved, only 100 facts shown |
| 5,001 rows on one saved local day, including a -4,950 compensating row | 834 ms; 11 pages | Exactly 50 surviving offerings, one rhythm date, positive source-linked evidence |
| Derived write deliberately sleeps for 3,000 ms | Cancelled and yielded after **1,525 ms** | Error recorded, next devotee proceeds, later retry recovers |

Additional passing assertions cover a correction accepted after a rebuild's fixed cutoff, a second requested rebuild consuming that correction, reversal from completed to paused, concurrent workers and retry idempotency, locked and flag-ineligible actors ahead of healthy actors, unavailable derived storage, test/production world separation, saved acceptance timezone, immutable canonical ledger rows, and canonical credit acceptance while derived projection writes fail.

A subsequent full repository run beside an optimized application build used the whole 1.5-second scheduling budget after 19 of the 25 actors. That is an expected yield, not a lost projection. The burst regression now resumes successive bounded turns and preserves its 2.5-second **active database work** budget; it does not add a fixed allowance and call that an end-to-end burst SLO. Actual gaps between two-second enqueue ticks, queue polling and client refresh remain excluded from that burst number. The separate real pg-boss test is the measured acceptance-to-publication check.

Earlier isolated repeats measured 152–195 ms for the single 2,501-row projection and 2,153–2,224 ms through the real queue. The table deliberately records the latest concurrent run rather than only the fastest sample.

## Reproduce

Start the existing local PostgreSQL service, then run from `dq-build`:

```sh
NURTURING_RUN_DB_TESTS=1 pnpm exec vitest run --reporter=verbose --silent=false \
  packages/domain/src/nurturing.test.ts \
  packages/db/src/nurturing.integration.test.ts \
  packages/db/src/nurturing.reliability.test.ts \
  apps/worker/src/jobs/nurturing.integration.test.ts
pnpm exec tsc -b packages/db apps/worker --pretty false
```

The integration tests require the existing local `satsang` test database administrator on `localhost:5442` only. They construct fresh random database names, run migrations before work, and drop those databases at completion. Without `NURTURING_RUN_DB_TESTS=1`, database tests remain skipped in the ordinary offline unit suite. Targeted Biome checks and the database/worker TypeScript build pass.

## Pilot scope and remaining qualification

The five-second target is verified from canonical acceptance to published projection for the measured local queue case. UI refresh, device suspension, network latency, production database size, pool pressure, and sustained concurrent load still need TEST-pilot measurement. Clients continue to show “updating” when a projection is incomplete or stale; a failed projection must never imply that accepted practice failed.

Reads remain bounded at 500 canonical rows per transaction. The current day must be retained in the checkpoint until its compensating rows reconcile, so checkpoint size depends on that day's ledger density; this run qualifies 5,001 rows on one day, not an unlimited import. All-time rhythm dates and lifecycle history are retained intentionally. Before a larger rollout, measure dense imports and a sustained multi-user backlog on the intended database class, including maximum checkpoint size and process memory. No truncation or credit loss is an acceptable workaround.

All nurturing feature flags remain OFF by default in migrations. These changes require no additional migration, provider credentials, paid calls, push messages, or production deployment.
